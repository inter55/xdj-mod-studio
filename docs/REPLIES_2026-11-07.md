# Replies — 2026-11-07

## Italy: "the (STEMS) file does not appear, FOLDER is EMPTY, searching STEMS finds nothing"

Measured first, emulator (deck's own 1.15 firmware, mini stick with a real
export.pdb and a `Get Lucky (ESQUIRE) (STEMS).wav` beside its MP3):

- The category list is `{ARTIST} {ALBUM} {TRACK} {KEY} {PLAYLIST} {HISTORY}
  {SEARCH} {FOLDER} {DATE ADDED}` — FOLDER is **below** SEARCH, as we said.
- Highlighting FOLDER shows `EMPTY` in the right-hand pane. That is what the
  user sees; it is not a preview that fills in.
- **The knob never opens FOLDER (emulator — WRONG, see the next bullet).**
  Three pushes (after an 80 M-step settle,
  twice in a row, and once after stepping away to `{DATE ADDED}` and back),
  and again after selecting the left-rail `rekordbox` and `USB` sources:
  the screen stays on the category list every time. Probe
  `build/folder_walk.py` + `build/folder_push3.py` + `build/folder_source.py`,
  screenshots in `build/folderwalk/`, `build/folderpush/`, `build/foldersrc/`.
  For contrast, pressing the knob on `{ARTIST}` does enter it (same probe run).
- **Hardware, same day: the emulator is wrong about this row.** On a real deck
  the knob opens FOLDER and lists the folders at the root of the stick. With
  only `/XDJ mod tests/` on the stick, that folder is the single entry shown,
  and pushing the knob on it lists the five files inside. `Contents` and
  `PIONEER` are not listed. So FOLDER is usable for a folder you create at the
  root, but not for a sidecar sitting in `Contents/Artist/Album/` — which is
  where the app writes one — and SEARCH is still database-only. Do not
  re-derive this row from `build/folder_*.py`; the emulator and the deck
  disagree and the deck wins.
- SEARCH cannot help: it queries the rekordbox database (`export.pdb`). A
  stems sidecar has no row there, which is exactly why it is missing from
  TRACK / ARTIST too. No amount of scrolling or spelling will find it.

So the guidance we shipped in 1.0.1 was wrong: MP3/M4A users were sent to a
list that does not open. Corrected in `README.md`, `site/index.html`,
`RELEASE_NOTES.md`, `studio/ui.html` and the completion message in
`studio/app.py`. The working route is replacement in place
(`tools/stems_replace.py`), which also keeps cues and the playlist slot.

Compiled **after** the hardware run, so the replies below say what the deck
actually does: FOLDER opens and lists the folders at the root of the stick,
which is why an ordinary export stick shows `EMPTY` — there is no folder at the
root for it to list, and `Contents` / `PIONEER` are not shown. The published
text (README, site, release notes, app completion message) now says that too;
`studio/ui.html` carried no FOLDER claim to fix. The working route stays
replacement in place (`tools/stems_replace.py`), which keeps cues and the
playlist slot.

## Why 1.0.2 (found while answering "is replacement out in 1.0.1?")

Three separate things, all measured on the SHIPPED archive
(`build/broken-zip/1.0.1-as-shipped.zip`), not on the working tree:

1. **The shipped 1.0.1 app has the replacement code and cannot run it.**
   `repo/studio/app.pyc` (mtime Nov 5 19:03, version string 1.0.1) contains
   `import stems_replace`, "replacing the track with its stems file" and the
   "stays in ARTIST / TRACK with its cues" message, and the UI sends
   `replace: true` on every Make stems. But the bundle has **no `vendor/`**,
   and `stems_replace` imports `rekordbox_pdb` from there -> every
   MP3/M4A/FLAC replacement died on ModuleNotFoundError. Same package is
   needed by `filter_playlists` (Make the whole set) and
   `onelibrary_to_pdb`, so those were dead in 1.0.1 too.
   `tools/stems_replace.py` also resolved `vendor` from the *current
directory*,
   not from its own path, so even a source checkout only worked when started
   from the repo root.
2. **`dist/XDJ-Mod-Studio-1.0.1-macOS.zip` (the re-cut one) is an OLDER app**
   than the archive users downloaded: its `studio/app.pyc` is 159,489 B dated
   Nov 4 22:14 and there is no `tools/stems_replace` in it at all; the shipped
   archive has 165,453 B dated Nov 5 19:03 plus the helper. `dist/` still holds
   that Nov 4 build. So the earlier "re-cut and verified" zip proved the
   signature/sidecar fix, not that the artefact was the shipped app. Do not
   publish it, and do not cut a 1.0.2 from `dist/` without a fresh build.
3. **Nothing caught either.** `make_app_zip.sh` checked sidecars, signature and
   file lists; no check asked whether the app could do its job.

Fixed: `vendor` is copied by `tools/build_studio.sh` and
`tools/build_studio_win.py`, `stems_replace` resolves its own path, the app's
`sys.path` includes `vendor`, and `tools/app_bundle_check.py` refuses a build
missing runtime modules (wired into both builders and into
`make_app_zip.sh --verify` and its post-zip proof).

Gate controls, all run: shipped 1.0.1 app -> FAIL (vendor/rekordbox_pdb x3);
same bundle with vendor copied in -> PASS; Windows `repo/` layout -> PASS and
FAIL without vendor; `dist/XDJ-Mod-Studio-1.0.1-macOS.zip` -> FAIL (no
stems_replace, no vendor). `stems_replace` now imports from an unrelated cwd
(/tmp). Not yet run: a full fresh app build (the next artefact to produce).
