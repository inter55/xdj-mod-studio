## #9 Unable to Write Mods to USB Stick (Win11)

Thanks, and thanks for finding the CPython issue: that is exactly it. To
write the mods file, the app records the install on an emulated deck, and
the app talked to that emulated deck over a Unix socket. Python on Windows
has no `socket.AF_UNIX`, so it stopped at about 2 %.

Fixed in 1.0.5 (https://github.com/inter55/xdj-mod-studio/releases/tag/v1.0.5): on Windows that connection now goes over the local
loopback (127.0.0.1; nothing outside your PC can reach it). I tested the
Windows code path on a Mac by forcing it, and the mods file it records puts
exactly the same bytes on the deck as before. I haven't run it on a Windows
PC myself, so please tell me whether it works for you once 1.0.5 is out.

## #10 Emulator failing to run (QEMU 3221225501)

Thanks for the screenshot. 3221225501 is 0xC000001D, Windows' "illegal
instruction". The Windows build compiled the emulated audio chip for the
build server's own processor (`-march=native` on a GitHub Xeon), so it used
CPU instructions that many desktop processors don't have. That is why it
crashed before showing anything, with both firmware choices.

1.0.5 (https://github.com/inter55/xdj-mod-studio/releases/tag/v1.0.5) builds it for any x86-64 PC from roughly 2009 on. Which CPU do you
have (Settings > System > About)? It would help me confirm this is the
whole story.

## #6 Hot cues D+ (reopened comment, 1.0.4 photo)

Thanks for the photo, it showed exactly what was wrong. The 8-pad view in
1.0.4 only looked in the hot-cue list of the `.DAT` analysis file. Exports
write D–H to a second, extended list in the `.EXT` file (the old list
dates from players with three hot cues), so on your tracks D–H looked empty,
and on pages 2/3 the pads fell back to A–C. The deck itself loads both
lists; we now read the extended one too.

I reproduced it in the emulator with a track exported that way: 1.0.4
fails it the same way (D plays A), and 1.0.5 passes. Same fix in the app's
hot-cue editor, which would also have dropped D–H when you edited a cue.
I haven't been able to try a Lexicon or VirtualDJ export myself, so a
report from your deck after reinstalling the mods with 1.0.5
(https://github.com/inter55/xdj-mod-studio/releases/tag/v1.0.5) would help a
lot.

D+ markers on the waveform and coloured hot cues aren't in this release;
both are still on the list. The extended list is also where the cue colours
live, which helps with that.

## Reddit, ThinkerSailorDJSpy (2026-11-09, hot cues jump to another track)

Thank you, this is a really useful report, and "dominant" tracks was the
clue. The deck keeps one buffer for a stick's track analysis, and BROWSE
fills it with whatever track is under the cursor when it shows that track's
details. Our hot-cue pages and the 8-pad view were re-reading that buffer
every time you tapped HOT CUE or changed page. So after browsing, they could
copy the BROWSED track's A–C onto the pads of the track you're playing: C on
Y jumps to X's C. The "dominant" track is just whichever one the cursor last
stopped on. It also explains pads lit A–C while the preview only shows B:
the pads were showing another track's cues, the preview your own.

It's fixed in the code: the pads now keep the deck's own A–C exactly as the
deck loaded them, and take D–H from that buffer only once per track, and
only after checking it really is the loaded track. I reproduced it in the
emulator by overwriting that buffer the way browsing does: the old code
writes the other track's cues, the new one doesn't. Not on a real deck yet,
and not released yet.

Markers: the waveform preview's cue markers are drawn by the deck itself,
and it only knows three hot cues, so D–H markers aren't there yet (on the
list). "D wouldn't trigger" may be the same bug; if it still happens after
the next update, tell me which page or view you were on.

The HOT CUE tab doing two jobs (tap = 8 pads / stock row, swipe = page) is
fair feedback too; I'll look at making that clearer.

## #11 Building mod Key Shift causing build error

Thanks for the full log, and great to hear the emulator runs and everything
else records now. For Live Key Shift the app has to let the emulated deck
run a small step of its own mid-install (a one-shot that patches the audio
chip), and on your PC that step never ran. I ran your exact selection
(RGB, pads, 8 hot cues, stems, themes, phase meter, key shift) on a Mac,
with the same kind of firmware snapshot and over the same Windows-style
connection: it passes every time, so this is something specific to Windows
I can't see yet.

1.0.6 (https://github.com/inter55/xdj-mod-studio/releases/tag/v1.0.6) waits
longer for that step and prints how long it took. The installer should
also print two lines just before "cave did not finish", starting `dbg` and
`status`, and they're missing from your log. Could you try again with 1.0.6
and paste everything from `5k` to the end, including those lines if they
appear? Until then, untick Live Key Shift when making the stick file; the
rest of the file is fine without it.
