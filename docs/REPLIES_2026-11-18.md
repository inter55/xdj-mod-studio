## Reddit / GitHub: LINK tracks in the theme colour; "RGB does nothing now"

Both of those are the same 1.1 change, and I can explain each.

The green: 1.1 made the blue waveforms follow your theme, which it does by
rewriting the deck's three blue palettes. A track loaded over LINK has no
colour data of its own, so the deck falls back to drawing from exactly those
palettes -- i.e. in forest green. That's the one place the theme colour was
never wanted. Fixed: with RGB or 3-BAND selected the fallback is now the
deck's own blue, and only BLUE/THEME still follows the theme (which is what
that label promises). It's built and passes in the emulator; not on my deck
yet, so it'll be in the next build rather than this one.

The "RGB does nothing" over LINK: 1.1 added a check so a track can never show
another track's colours. Before, a LINK load didn't have its own colour data
either -- the mod silently took whatever analysis the deck's cache last held,
i.e. a different track's colours. That looked like RGB working. Now the check
(properly) refuses and you get blue. Real colours on a LINK track means
reading the analysis file from the other deck over the link, which is a
separate piece of work, not a regression I can flip back on.

### What his studio.log actually says (2026-11-18, log arrived)

`studio.log` (the app's console) has no deck install in it at all -- no
step lines -- but it does contain the same traceback three times:

```
theme tables skipped: 2802
Exception in thread emu-mods:
  studio\emuhost.py:192 work -> emu\ui.py:639 apply_wave
  -> tools\perform_pads.py:2835 install -> 2804 blobs
  AssertionError: 2802
```

Both symptoms are ONE failure. `theme_switch.own_art()` builds its tables
by calling `perform_pads.blobs()` (the pads' own artwork is part of the
artwork it themes), so the theme-table message and the emulator traceback
are the same raise.

What 2802 is: `aafont.blob("tab")` -- the PERFORM-screen tab font table.
Its layout is `68 + 4*n + H*sum(width)`; with n = 40 glyphs, H = 9 rows and
sum(width) = 286 that is exactly `68 + 160 + 9*286 = 2802` bytes, which is
the documented Windows Arial size of the tab table (see the comment above
`FONTT` in `tools/perform_pads.py`). The assert that fires is
`assert FONTT + len(ft) <= FONTK, len(ft)` -- a bare number, which is why
the log reads as an unrelated crash.

This cannot happen in 1.1: since 2026-10-21 `aafont._render` squeezes the
Arial stand-in to the Mac's widths (measured here today: tab 2415 B, key
2770 B, pad 1804 B with Arial), and the tab slot has been 2832 B since the
FONTT fix (it holds 2802 with 30 B to spare). So **the app he is running is
a pre-0.9.6 Windows build** --
the exact failure `RELEASE_NOTES.md` records for the first Windows
installer ("`AssertionError: 2802` ... fixed in 0.9.6"). In that build the
PERFORM pads cannot be built at all, and 8 hot cue pages refuse to install
without pads, so nothing reaches the deck: "reports success, CDJ
unmodified" is that build's reporting, not a cable problem.

Action on our side (not done yet): check that the Windows asset on the 1.1
release is a fresh CI build and not an old artifact re-attached -- the
workflow only attaches `XDJ-Mod-Studio-Windows.zip` when it is run with a
release tag, so a hand-attached older zip stays there and looks current.
Worth making the geometry asserts name their table in 1.1.1
(`assert ... <= FONTK, f"tab font {len(ft)} B > slot"`) -- this report cost
time only because the message was a bare number.
